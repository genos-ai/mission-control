Revised plan — concrete amendments

  1. §10 workflow. Replace assemble_case + record_rejection predecessors with explicit node_type: merge join nodes, then chain the agent_step/tool_call after the merge. Accept the diagram complication.
  2. §10 trigger surface. Drop match_patterns. UI-only trigger. Chat-trigger promise was unworkable — match_patterns can't carry nested context.
  3. §17 / GAPS.md. Tone-shift. Strip "theatre", "roast", "illustrative only". Use "demo-scope", "stub", "representative". Add **Distribution: Internal team only.** header. Decide explicitly whether GAPS.md ships to the repo or stays private.
  4. §12.5 / SSE. Either extend JWT TTL to comfortably exceed longest demo run (30+ min), add an ?after_event_id= cursor in the demo page only, or add a "Refresh / Resume" button so the presenter has graceful recovery. Choose one before commit 1.
  5. §3 / §10 four-eyes. Drop the four-eyes path entirely OR commit to real identity separation (two distinct test users with distinct sessions). Do not ship the one-person-clicks-twice version. Recommended: drop.
  6. §6 / §11.3 seeder + §11.1 API. Make failures loud. Seeder WARNs if flag is on and zero demo agents in catalog. POST /start pre-flights catalog presence and returns 503 Demo Not Seeded with a clear instruction string.
  7. §7.2 supervisor. Drop the REUSE-WITH-CONFIG claim. Build the demo supervisor fresh — own output schema, own deps, own tools. Treat as the sixth from-scratch agent.
  8. §18 status checklist. Add at top: named exec sponsor committed in writing + fixed walkthrough date on calendar, both before commit 1. If either is empty, the plan does not proceed.

Pre-launch checklist

  1. Before commit 1. Get sponsor + date in writing. Read _should_skip and redesign convergence with merge nodes. Decide four-eyes outcome (drop vs real separation).
  2. Before commit 5 (workflow template). Build a one-off test workflow that exercises multi-decision-branch convergence in isolation. Confirm assumed behaviour. If assumption fails, redesign.
  3. Before commit 9 (frontend stream view). Run a 20-minute demo in a browser tab and confirm the SSE stream survives a JWT refresh without losing a gate event. If it doesn't, fix before commit 10.
  4. Before demo day, T-24h. Pre-flight script: all 6 demo agents present + enabled in agent_catalog, Redis up, no concurrent demo run in flight, presenter has admin token cached locally.
  5. Before demo day, T-1h. Run all three fixtures end-to-end on the demo backend. Any path fails → don't present.
  6. Before GAPS.md is committed. Second pair of eyes on tone. Strip flourishes. Decide repo vs wiki vs burn.

Failure deep-dives

#1Verified in code · Most likely
Plan 75 convergence assumption is wrong
Failure story
Day 3 of impl. assemble_case wired as agent_step with three decision-routed predecessors. Clean-path smoke test: route_qa returns pass; the other two get _skipped. assemble_case never runs — status SKIPPED. The skip propagates because _should_skip only exempts node_type: merge. §13 Q7 was supposed to catch this but the "reference precedent" template doesn't actually exercise this pattern. Under time pressure the team converts to merge + downstream node, blowing the clean three-path visual. The architect spends the first five minutes of the walkthrough explaining six rectangles where the slide shows three.
Underlying assumption
Decision-node skip propagation is graph-aware (a skipped branch satisfies its successor), when in fact _should_skip propagates through any non-merge dependency unconditionally.
Early warning signs
First dry-run convergence step shows SKIPPED despite a predecessor branch completing.
Grep config/workflow_templates/*.yaml for steps with depends_on ≥2 decision/condition nodes returns zero non-merge hits.
#2Verified in code
Chat trigger can't supply applicant context
Failure story
UI works beautifully. Two weeks later a PM tries "demo onboard uk" in chat. Director matches match_patterns, calls run_workflow with context_overrides=None (signature is dict[str, str], can't carry nested applicant anyway). Workflow launches with context: {applicant: {}, fixture_name: ""}. The first agent hallucinates a verdict for "John Doe, address unknown". The stakeholder notices; the PM doesn't. Retrofit options both bad — team quietly removes match_patterns. "UI + chat" becomes "UI only" in a README diff nobody reads.
Underlying assumption
match_patterns is equivalent to the UI trigger, when it's a context-free pattern match — can launch a workflow but cannot supply structured parameters.
Early warning signs
run_workflow's signature is context_overrides: dict[str, str] | None — flat string dict.
No existing template uses match_patterns with required nested parameters; deep-research only works because its defaults are safe.
#3Plausible · Reputational
GAPS.md becomes the vendor's kill-shot
Failure story
UK challenger bank, warm intro from a board member. Two days before the meeting, the bank's vendor-risk analyst does her pre-read. She finds 77-gaps-demo-uk-onboarding.md, copy-pastes §17 into a one-page memo titled "Vendor Self-Disclosure: Mission Control", sends it with one line: "Their own document calls two of six agents 'LLM theatre' and the audit trail 'not immutable'. Recommend we decline." The CRO never takes the meeting. Internally, a skeptical exec forwards the same §17 under the subject "Per the team's own assessment". "LLM theatre" — written by us, about us — becomes the meme that defines the project in three rooms we weren't in.
Underlying assumption
The audience for "radical honesty" will always be the original team and a charitable exec in the same room — never a hostile reader, a procurement gatekeeper, or a screenshot taken out of context.
Early warning signs
GAPS.md uses rhetorical flourishes ("roast", "theatre", "illustrative only") rather than neutral engineering language.
No one asks "who else might read this, and what would they screenshot?" before commit.
#4Verified in code · Live-demo risk
SSE reconnect loses the gate event
Failure story
Twelve minutes into the adverse_media walkthrough, JWT expires mid-stream. useFetchSse exits its loop, hits 401, calls refreshTokens(), then setTimeout(backoff) — minimum 1s. During the reconnect gap, the workflow emits the GateApprovalRequested for the second approver. New connection picks up future events only — the gate event is lost. GateApproval never mounts. The Approve button never appears. Workflow sits in WAITING_FOR_APPROVAL. Presenter says "give it a moment" three times, then refreshes. Forty seconds of dead air in front of execs.
Underlying assumption
SSE delivery is reliable enough that the frontend has no replay-from-cursor mechanism — reconnect resumes from "now," not from the last seen event ID.
Early warning signs
Backend SSE endpoint accepts no Last-Event-ID header or ?since= cursor.
JWT TTL shorter than the longest demo run.
#5Most dangerous · Reputational
Four-eyes credibility collapse
Failure story
34 minutes in. Presenter approves the first gate, then — without switching user, without moving the mouse — approves the second. Both attributed to the same session. Sarah Whitfield, ex-PRA supervisor on the prospect's risk committee, waits for the disclaimer, then asks evenly: "So what I just watched isn't four-eyes. It's one person clicking twice and the system letting them. Is dual-control enforcement a roadmap item, or does the platform genuinely not model identity separation?" Presenter says both — the worst possible answer. Two weeks later the recording surfaces in the prospect's compliance Slack with the timestamp pinned to the double-click. Verbal disclaimer isn't in the recording. Deal stalls in SMCR review for questions the platform was never designed to answer.
Underlying assumption
A verbal disclaimer can neutralise a visual demonstration of a regulatory control being violated, in front of an audience trained to trust what they see over what they're told.
Early warning signs
During dry-run, a non-compliance reviewer says "wait, you clicked it yourself twice?" — and the team rationalises rather than redesigns.
GAPS.md entry on four-eyes is a defensive paragraph, not a crisp one-line known limitation.
#6Operational
The two-step seed trap
Failure story
13:47. Cara flips the flag, restarts, clicks the tile. Form posts. Workflow ID comes back. Four seconds later: AgentNotFoundError: demo.uk.onboarding.supervisor.agent. The toggle-only seeder ran successfully, logged "0 entries updated", exited 0. No alarm. RUNBOOK mentioned admin seed-catalog --force on page 2 in a paragraph she'd skimmed because the email said "just a flag flip." Exec walkthrough is at 14:00. She pages the demo author at 13:54 — he's on a flight. Tries the force-seed at 13:57; admin token IAM round-trip takes six minutes. Execs see a spinning loader.
Underlying assumption
A two-step procedure (seed-then-toggle) will be reliably executed in the correct order by an operator who treats "enable the demo" as a single atomic action.
Early warning signs
Toggle-only seeder logs "0 entries updated" — indistinguishable from "already correct" vs "rows don't exist".
No startup validation that the referenced catalog rows exist; failure surfaces only at dispatch.
#7Verified in code
Supervisor reskin breaks on semantics, not surface
Failure story
Audit saw "supervisor — Haiku, three tools, structured output" and concluded REUSE-WITH-CONFIG. Six months in, the implementer discovers mission.supervisor.agent is a hardwired post-run autonomy classifier. create_event_agent returns SupervisorDecision — a closed enum of wait | advance | refine | propose-complete | escalate — meaningless for onboarding triage. All three "reusable" tools hardcode-import adapters keyed off mission_id assuming a MissionPlan row exists. Demo has no MissionPlan. Tools return {"error": "..."}. Implementer Frankensteins a parallel deps class, stubs the tools, and force-maps SupervisorDecision to onboarding actions. QA later asks "why does the demo supervisor sometimes return propose-complete after a KYC step?" Nobody can answer.
Underlying assumption
"Same agent shape" (LLM + tools + prompt) is equivalent to "same agent semantics," ignoring that SupervisorDecision's output enum and mission_id-keyed introspection are load-bearing for the autonomy loop.
Early warning signs
Plan doesn't specify which factory (create_event_agent vs create_agent) it reuses.
Plan never addresses what SupervisorDecision's five-action enum means in an onboarding context.
#8Strategic · Opportunity cost
The demo nobody asked for
Failure story
Branch shipped clean in early June. Walkthrough slips to mid-July (quarter-end), then August (one exec on leave), then "let's roll it into the September offsite." At the offsite it gets 8 minutes after lunch to an audience of the COO's chief of staff, two engineering leads, and a PM who already uses the real tool. COO joins for the last 3 minutes, says "neat, send me the recording," and pivots. No recording requested. No follow-up. Meanwhile the platform team moved on; Plan 75 shipped a real customer-facing capability in August and consumed all the oxygen. By October, the catalog_seeder has been refactored twice, gate.yaml shape has drifted, the demo can't be driven. Q4 retro flags "the two weeks on Plan 77" as why we require a signed exec commitment before demo builds.
Underlying assumption
Executive attention is a resource you can earn by building something impressive — rather than a calendar slot you must secure in writing before you write a line of code.
Early warning signs
No exec name on the plan as requesting sponsor — only "executives" (plural, abstract).
Walkthrough date is "TBD" or floating, not a fixed calendar invite predating commit 1.
