## 21. SSE Streams

**Router prefix:** `/streams` · **File:** `api/v1/endpoints/streams.py`

All SSE endpoints use `SseUser` auth (short-lived SSE token, JWT query param, or Bearer header). API keys are **not** accepted on streaming endpoints.

**Response headers:** `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`

| Path | Summary | Channel | Access Control |
|------|---------|---------|----------------|
| `GET /streams/runs/{session_id}` | Stream execution events for a session (agent thinking, tool calls, cost updates) | `mission_events:{mission_id}` filtered by session_id | Admin, session owner, or mission member |
| `GET /streams/missions/{mission_id}` | Stream all events across all sessions in a mission | `mission_events:{mission_id}` (unfiltered) | Admin, owner, or mission member |
| `GET /streams/notifications?user_id={id}` | Stream user notifications (gate approvals, completions, budget warnings) | `notify:{user_id}` | Own notifications only (admin can subscribe to any) |

**Connection lifecycle:**
1. Client connects with `?token=<sse_token>` or `Authorization: Bearer <jwt>`
2. Server sends: `event: connected\ndata: {"session_id": "..."}\n\n`
3. Events stream as: `event: {event_type}\ndata: {json}\n\n`
4. Keepalive: `:` comment sent every 1–5 seconds when idle

**Additional streaming endpoint:**
- `POST /sessions/{session_id}/messages` — sends a chat message and streams the agent's response as SSE (in `sessions.py`)
- `POST /agents/chat/stream` — single-agent chat streaming (in `agents.py`)

## 23. SSE Event Type Registry

All events extend `SessionEvent` with base fields: `event_id`, `event_type`, `session_id`, `timestamp`, `source`, `correlation_id`, `trace_id`, `metadata`.

Events are classified into three categories for frontend rendering:
- **execution** — patterns matching `^(plan\.|agent\.|workflow\.|convergence\.|execution\.|task\.)`
- **chat** — patterns matching `^(user\.message\.|assistant\.message\.|agent\.response\.complete)`
- **system** — everything else

### User Events

| Event Type | Class | Key Fields |
|------------|-------|------------|
| `user.message.sent` | `UserMessageEvent` | `content`, `channel`, `attachments[]` |
| `user.approval.granted` | `UserApprovalEvent` | `decision`, `approval_request_id`, `reason?`, `modified_params{}` |

### Agent Events

| Event Type | Class | Key Fields |
|------------|-------|------------|
| `agent.thinking.started` | `AgentThinkingEvent` | `agent_id` |
| `agent.tool.called` | `AgentToolCallEvent` | `agent_id`, `tool_name`, `tool_args{}`, `tool_call_id` |
| `agent.tool.returned` | `AgentToolResultEvent` | `agent_id`, `tool_name`, `tool_call_id`, `result?`, `status`, `error_detail?` |
| `agent.response.chunk` | `AgentResponseChunkEvent` | `agent_id`, `content`, `is_final` |
| `agent.response.complete` | `AgentResponseCompleteEvent` | `agent_id`, `full_content`, `input_tokens`, `output_tokens`, `cost_usd`, `model` |

## 25. Auth Flows

### JWT Login Flow

```
POST /api/v1/auth/login
Body: { "email": "...", "password": "..." }
  → 200: { data: { access_token, refresh_token, token_type: "bearer" } }
  → 401: AUTH_INVALID_CREDENTIALS

POST /api/v1/auth/refresh
Body: { "refresh_token": "..." }
  → 200: { data: { access_token, refresh_token, token_type: "bearer" } }
  → 401: AUTH_TOKEN_EXPIRED
```

### API Key Auth

```
Any endpoint (except SSE streams):
  Header: X-API-Key: <key>
  → Resolved via AuthService.resolve_api_key()
  → Fallback: AuthService.resolve_legacy_key() (admin key)
```

### SSE Token Flow

SSE endpoints do not accept API keys. Use the short-lived SSE token:

```
1. POST /api/v1/auth/sse-token (with JWT Bearer)
   → 200: { data: { token: "<sse_token>" } }
   Token stored in Redis with 30s TTL, single-use.

2. Connect to SSE:
   GET /api/v1/streams/missions/{id}?token=<sse_token>
   → Redis lookup, token deleted on use.
   → Fallback: raw JWT decode if Redis lookup fails.
   → Fallback: Authorization: Bearer <jwt> header (non-browser clients).
```

### Auth Resolution Order (REST)

1. `Authorization: Bearer <jwt>` header → JWT decode
2. `X-API-Key` header → per-user API key lookup
3. `X-API-Key` header (fallback) → legacy admin key
4. None → `AuthenticationError`

### Auth Resolution Order (SSE)

1. `?token=<sse_token>` query param → Redis single-use token
2. `?token=<jwt>` query param (fallback) → raw JWT decode
3. `Authorization: Bearer <jwt>` header → JWT decode
4. None → `AuthenticationError`

### Auth Level Summary

| Level | Dependency | Description |
|-------|-----------|-------------|
| **Public** | None | No authentication required |
| **Authenticated** | `CurrentUser` | Valid JWT or API key |
| **Admin** | `AdminRole` | Authenticated + `system_role = "admin"` |
| **SSE** | `SseUser` | SSE token, JWT query param, or Bearer header |

## 26. Response Envelope

All endpoints wrap responses in a standard envelope defined in `schemas/base.py`.

### Success Response — `ApiResponse<T>`

```json
{
  "success": true,
  "data": { ... },
  "error": null,
  "metadata": {
    "timestamp": "2026-04-23T12:00:00Z",
    "request_id": "uuid"
  }
}
```

### Error Response — `ErrorResponse`

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "RES_NOT_FOUND",
    "message": "Mission not found",
    "details": null
  },
  "metadata": {
    "timestamp": "2026-04-23T12:00:00Z",
    "request_id": "uuid"
  }
}
```

### Validation Error Response

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VAL_REQUEST_INVALID",
    "message": "Validation failed",
    "details": {
      "validation_errors": [
        { "field": "email", "message": "field required", "type": "missing" }
      ]
    }
  },
  "metadata": { ... }
}
```

### Frontend Unwrap Pattern

The frontend reads `response.json().data` via a shared `unwrap()` helper. All API calls should expect this envelope.

## 27. Pagination

Endpoints that return lists support offset-based or cursor-based pagination. Defined in `core/pagination.py`.

### Query Parameters

| Param | Type | Default | Description |
|-------|------|---------|-------------|
| `limit` | int | Config `pagination.default_limit` | Items per page (capped at `pagination.max_limit`) |
| `offset` | int | 0 | Skip N items (offset-based) |
| `cursor` | string | — | Opaque cursor for cursor-based pagination |

### Paginated Response Envelope

```json
{
  "success": true,
  "data": [ ... ],
  "error": null,
  "metadata": { "timestamp": "...", "request_id": "..." },
  "pagination": {
    "total": 42,
    "limit": 20,
    "cursor": null,
    "next_cursor": "eyJpZCI6IjEyMyJ9",
    "has_more": true
  }
}
```

### Endpoints Supporting Pagination

- `GET /sessions` — offset + cursor
- `GET /sessions/{id}/messages` — offset + cursor
- `GET /notes` — offset
- `GET /executions` — offset
- `GET /admin/users` — offset
- `GET /missions/{id}/learnings` — offset
- `GET /missions/{id}/intent/history` — offset
- `GET /knowledge/learnings` — offset
