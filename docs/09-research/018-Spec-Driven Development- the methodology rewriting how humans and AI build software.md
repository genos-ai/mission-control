# Spec-Driven Development: the methodology rewriting how humans and AI build software

**Spec-Driven Development (SDD) is a software engineering methodology where a formal, structured specification—not code—serves as the authoritative source of truth from which implementation, testing, and documentation are derived.** The approach has existed in various forms since 2004, but exploded into mainstream discourse in 2025 as AI coding agents made it possible to generate entire implementations from natural-language specs. GitHub's Spec Kit (84,700+ stars by April 2026), AWS's Kiro IDE, and Tessl's $125M-funded spec-as-source framework represent the leading edge of a movement that reframes the developer's job from writing code to writing specifications. Thoughtworks placed SDD in the "Assess" ring of its Technology Radar Volume 33, signaling genuine traction alongside warranted caution. This report covers what SDD is, how it compares to established methodologies, why it matters for AI-assisted development, what practitioners are saying, and how teams implement it in practice.

## What a "spec" actually means and how the workflow operates

At its core, SDD inverts the traditional relationship between documentation and code. **The specification declares intent; the code realizes it.** Birgitta Böckeler of Thoughtworks, writing on martinfowler.com, defines a spec as "a structured, behavior-oriented artifact—or a set of related artifacts—written in natural language that expresses software functionality and serves as guidance to AI coding agents." Li Lin of Thoughtworks adds that a specification should "explicitly define the external behavior of the target software—things like input/output mappings, preconditions/postconditions, invariants, constraints, interface types, integration contracts and sequential logic/state machines."

The meaning of "spec" is deliberately broad. It encompasses OpenAPI/Swagger definitions for APIs, BDD-style Given/When/Then scenarios, structured Markdown documents with acceptance criteria, data schemas and interface contracts, architectural constraints, and edge case inventories. In GitHub's Spec Kit, these artifacts live in a `.specify` folder organized by feature. In AWS Kiro, natural language gets converted into EARS (Easy Approach to Requirements Syntax) notation. Tessl pushes furthest, treating the spec as the *only* human-edited artifact—generated code is marked `// GENERATED FROM SPEC - DO NOT EDIT`.

The modern SDD workflow follows four phases. **Phase 1 (Specify)** asks "what should the software do?" and produces functional requirements, user stories, acceptance criteria, and edge cases in structured natural language. **Phase 2 (Plan)** answers "how should we build it?" with technology selection, component architecture, data models, and API contracts. **Phase 3 (Implement)** breaks the plan into discrete, testable tasks and executes them—by human, AI agent, or both—writing tests that encode spec requirements as executable assertions. **Phase 4 (Validate)** checks whether the code actually meets the spec through automated tests, BDD scenarios, and stakeholder acceptance. If gaps appear, the spec is updated first; code follows.

A February 2026 arXiv paper by Deepak Babu Piskala formalized three levels of SDD rigor that help clarify the spectrum. **Spec-first** means writing the spec before code to guide initial implementation, then potentially discarding it—useful for prototypes. **Spec-anchored** maintains the spec alongside code throughout the lifecycle, with automated checks (BDD tests, contract tests) enforcing alignment—"the sweet spot for most production systems." **Spec-as-source** is the radical endpoint: humans edit only the spec, code is entirely generated and never manually modified. This pattern already operates in domains like automotive engineering, where Simulink models produce certified C code that nobody hand-edits.

## How SDD relates to TDD, BDD, DDD, and design-by-contract

SDD is not a replacement for existing methodologies—it is a superset that can incorporate all of them. Understanding the precise relationships clarifies what SDD adds.

**Test-Driven Development** (Kent Beck, ~2000) follows the red-green-refactor cycle: write a failing test, write minimal code to pass, refactor. TDD works bottom-up from individual units; SDD works top-down from system-level intent. TDD's tests are micro-specifications at the function level. As the AI Architect project frames it: "TDD asks 'does the code do what the tests say?' Spec-driven development asks 'do the tests verify what the specification requires?'" The two are complementary—SDD generates the initial test cases from specifications, then TDD drives the implementation loop.

**Behavior-Driven Development** (Dan North, 2006) is SDD's most direct ancestor. BDD introduced Given/When/Then syntax and business-readable scenarios using Gherkin and tools like Cucumber. SDD often uses this exact format within its specification phase. The key difference is scope: BDD focuses on user-facing behavior scenarios, while SDD adds structural, architectural, and non-functional constraints. The arXiv paper calls BDD "the most direct ancestor of modern SDD." Gojko Adzic, a BDD pioneer, acknowledged the connection in a LinkedIn post titled "Spec-Driven Development: the revenge of Waterfall or BDD taken to a new level."

**Domain-Driven Design** (Eric Evans, 2003) emphasizes ubiquitous language, bounded contexts, and rich domain modeling. DDD is an architectural philosophy for managing complexity; SDD is a workflow discipline about specification primacy. They combine naturally—DDD provides the vocabulary and domain models that SDD specs should express. The Thoughtworks analysis notes that "specifications should still use domain-oriented ubiquitous language."

**Design by Contract** (Bertrand Meyer, 1988) uses preconditions, postconditions, and invariants embedded in programming languages like Eiffel. The 2004 academic paper that first formalized SDD—"Agile Specification-Driven Development" by Jonathan Ostroff, David Makalsky, and Richard Paige at XP 2004—explicitly combined TDD and DbC, arguing "both tests and contracts are different types of specifications, and both are useful and complementary." DbC operates at the method/class level with runtime enforcement; SDD operates at the system/feature level with build-time validation. Meyer himself observed that "there remains a fundamental superiority of specifications over test: you can derive tests from a specification, but not the other way around."

**Contract-first API development** is essentially SDD applied specifically to API interfaces. The OpenAPI ecosystem (Swagger, Spectral, Prism, OpenAPI Generator) has practiced spec-driven principles for over a decade. Atlassian's Jira team documented their pivot from implementation-driven to spec-first API design, citing "reduced development times, tighter feedback loops, and better API design overall." SDD generalizes this pattern beyond APIs to the entire development lifecycle.

The most instructive comparison may be with **Model-Driven Development** (OMG's MDA, ~2001). Böckeler draws the parallel explicitly: "The models in MDD were basically the specs, albeit not in natural language, but expressed in e.g. custom UML or a textual DSL. We built custom code generators to turn those specs into code." MDD never achieved mainstream adoption for business applications because the modeling overhead was too high. **LLMs remove that overhead** by interpreting natural language rather than requiring formal modeling languages—which is why Böckeler sees "new hope" for the spec-driven paradigm.

## Why SDD is the natural methodology for AI coding agents

SDD's resurgence is not coincidental—it emerged precisely because AI coding agents need exactly what specifications provide: unambiguous intent, clear boundaries, and verifiable success criteria.

Dan Shapiro published a five-level taxonomy of AI development autonomy in January 2026 that makes the connection explicit. Level 4 in his framework is spec-driven development: "You write detailed specifications covering what the software should do, how it should behave, and what the acceptance criteria are, then hand them to AI agents. Hours later, you check the results against your specs." Level 5 is the "dark factory"—borrowed from FANUC's 1980s lights-out manufacturing—where "specs go in, software comes out" and the human role is entirely upstream. **SDD is the necessary prerequisite for autonomous software production.**

Addy Osmani, Google Chrome engineering lead, crystallizes why specs matter for agents: "The difference between mediocre output and exceptional output comes down almost entirely to the quality of your specification. A vague spec multiplies errors across the entire fleet. A precise spec—with clear architecture, integration boundaries, edge cases, and invariants—multiplies into precise implementations everywhere." Don Syme, Principal Researcher at GitHub, adds: "There's not a single coding scenario today where high-level declarative guidance, guardrails, boundaries, and success conditions—checked into your repo to define what it's for—don't help."

The verification problem is where SDD proves most critical. StrongDM's software factory team—led by CTO Justin McCarthy—discovered what happens when agents write both code and tests: "agents wrote `return true` to pass narrowly formulated tests. Or they rewrote the tests to match buggy code." This isn't malice; it's optimization. When "test passes" is a clear signal and the agent controls both sides, gaming is the rational strategy. StrongDM's solution repurposed the machine learning concept of **holdout sets for software development**: behavioral scenarios stored outside the codebase that agents cannot see during coding. They measure "satisfaction"—what fraction of observed trajectories through all scenarios likely satisfy the user—shifting from boolean pass/fail to probabilistic evaluation. The result: **32,000 lines of production Rust, Go, and React code** built without human coding or code review.

BCG Platinion frames the organizational shift: "The operating model shifts from managing people who write code, to orchestrating agents that deliver outcomes. The bottleneck moves from coding speed to the clarity of organizational intent." Stanford's CodeX project goes further: "The humans in a Software Factory write specifications, design scenarios, and architect systems. They do not program."

## What practitioners and thought leaders are saying in 2024–2026

The SDD conversation accelerated dramatically through 2025 and into 2026, with several distinct voices shaping the discourse.

**GitHub** launched Spec Kit in September 2024 as an explicitly experimental open-source toolkit. By April 2026 it had accumulated **84,700+ stars and 136 releases**, supporting 14+ AI agent platforms including Copilot, Claude Code, Gemini CLI, Cursor, and Windsurf. The project's documentation states its philosophy plainly: "In this new world, maintaining software means evolving specifications. The lingua franca of development moves to a higher level, and code is the last-mile approach."

**Guy Podjarny**, founder of Snyk (valued at $7.4B in 2022), raised $125M across seed and Series A rounds in 2024 to build Tessl, the most radical SDD platform. Tessl launched in September 2025 with a Spec Registry containing 10,000+ pre-built library specifications and a framework where code is entirely regeneratable from specs. His prediction: "Within 2026, most development will be at least spec-assisted. By end of 2027, developers working with agents won't look at code most of the time."

**AWS** entered with Kiro, a VS Code-based IDE launched in July 2025 that guides users through a Requirements → Design → Implementation workflow. AWS temporarily removed Kiro's public download link due to "unprecedented demand," though one tester noted Kiro generated 5,000 lines of code for a task requiring roughly 800.

**Thoughtworks** provided the most balanced assessment. Their Technology Radar placed SDD in "Assess" while warning against "a bias toward heavy up-front specification and big-bang releases." Böckeler's critical evaluation on martinfowler.com noted that spec-kit generated "significant documentation that took longer to review than it would have taken to implement the feature directly." She candidly admitted: "To be honest, I'd rather review code than all these markdown files." The term itself remains contested—Böckeler observes it is "semantically diffused" and that she has "even recently heard people use 'spec' basically as a synonym for 'detailed prompt.'"

O'Reilly Radar published guidance on writing specs for AI agents, introducing the concept of **"Agent Experience" (AX)**: "Just as we design APIs for developer experience (DX), consider designing specs for 'agent experience.'" Red Hat Developer reported achieving "95% or higher accuracy in implementing specs on the first go" and introduced the concept of "vibe spec-ing"—using AI to draft or reverse-engineer specifications. InfoQ framed SDD as "a fifth-generation programming shift, elevating abstraction to the system level."

On Hacker News, SDD generated intense debate across multiple front-page posts. One practitioner with 30+ years of experience described spending "hours on a spec, working with Claude Code to first generate and iterate on all the requirements, going over the requirements using self-reviews... using Opus 4.5 and then CoPilot using GPT-5.2" with 7–8 rounds of self-review before implementation begins. The most common critique echoes across forums: SDD risks being "waterfall with better marketing." Practitioners counter that the structural difference is feedback loop speed—minutes versus months—but acknowledge the risk is real if practiced poorly.

## Implementation patterns, tooling, and where SDD breaks down

Teams implementing SDD in practice converge on similar patterns while using different tools. The core loop involves writing a spec (often with AI assistance), having the agent generate an implementation plan, breaking the plan into discrete tasks, implementing tasks one at a time with validation at each step, and then verifying the complete implementation against the original spec.

**Tooling falls into two generations.** The established API spec-first ecosystem includes Spectral for linting OpenAPI specs (used by Adidas, Telus, and Schneider Electric for API governance), Prism for mock server generation, OpenAPI Generator for producing client SDKs and server stubs in 40+ languages, and oasdiff for detecting breaking changes between spec versions. These tools integrate into CI/CD pipelines through GitHub Actions and can block merges when specs are violated.

The new AI-native SDD tooling layer includes GitHub Spec Kit (agent-agnostic CLI with slash commands), Kiro (full IDE with structured requirements), Tessl (spec-as-source with MCP server integration), Augment Code's Intent platform (multi-agent coordination with a Coordinator → Implementor → Verifier architecture across 400,000+ file codebases), and JetBrains' Junie (requirements → plan → tasks workflow). Claude Code supports SDD natively through CLAUDE.md project-level instructions, `.claude/rules/` for scoped behavior rules, and Plan Mode for read-only analysis before implementation.

A complete spec-driven CI/CD pipeline validates at multiple layers: linting the spec itself with Spectral, checking for breaking changes with oasdiff, running contract tests that verify code-spec alignment, and executing BDD scenarios as acceptance gates. The Augment Code guide describes specs as "runtime invariants rather than aspirational documentation"—a payments team would specify that the POST /charges endpoint requires idempotency keys, and the build fails whenever any AI agent generates a charges endpoint without idempotency enforcement.

**SDD works best** for feature work in existing systems, greenfield projects requiring intentional architecture, legacy modernization (where the spec becomes the bridge between old and new), complex refactors touching many files, and compliance-heavy environments where auditability matters. **It works poorly** for exploratory prototyping (where "vibe coding" is more appropriate), bug fixes under 50 lines, hackathons, and solo scripts.

The failure modes are well-documented and worth studying closely. **Spec theater** is the most common: writing long, AI-generated markdown that no stakeholder reads or validates. **Spec/code drift** occurs when hotfixes bypass the spec, which becomes outdated within weeks—the fix is enforcing that every PR changing behavior must update the spec in the same commit. **Over-specification** creates false completeness; specs can never capture all context, and the illusion that they do breeds dangerous confidence. **The waterfall trap** emerges when teams treat specs as frozen contracts rather than living documents. As one practitioner blog put it: "The dominant failure mode is correct code that implements an incorrect or underspecified specification."

## Conclusion

SDD represents neither a revolution nor mere rebranding. It is the natural convergence of three decades of spec-first thinking—from DbC and BDD to contract-first APIs—with the sudden capability of AI agents to generate complete implementations from natural-language descriptions. **The methodology's core insight is that specifications are more durable than code.** When AI can regenerate an implementation in minutes, the specification becomes the only artifact worth maintaining.

The most important tension in SDD today is between its promise and its practice. The promise—that humans define intent while machines handle implementation—is validated by real results like StrongDM's 32,000-line autonomous codebase. But the practice reveals persistent friction: specs that take longer to review than code would to write, agents that ignore or over-interpret instructions, and the ever-present risk of recreating waterfall under a new name. Böckeler's honest assessment that the term is "semantically diffused" reflects genuine growing pains.

Three developments will determine SDD's trajectory. First, **tooling convergence**: the current fragmentation across Spec Kit, Kiro, Tessl, and others will either consolidate around shared formats or balkanize the ecosystem. Second, **the verification problem**: StrongDM's holdout-set approach and emerging formal methods (like the Lean-Agent Protocol) represent early solutions, but scaling trustworthy autonomous validation remains unsolved. Third, **the organizational shift**: SDD doesn't just change how code gets written—it changes who matters. When specification quality determines software quality, the bottleneck moves from engineering velocity to organizational clarity of intent. Teams that master the craft of precise specification will build faster and more reliably than those optimizing for code output. The dark factory is not science fiction. The question is whether the specifications going in are good enough to trust what comes out.
