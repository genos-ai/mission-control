**Director proactive follow-up: wake on completion events instead of waiting for the human to prompt again:** Today when the user asks the Director to run a task or workflow, it responds in chat with "I've kicked that off — I'll check back when it completes" and then the PydanticAI turn ends. The agent is dead until the user types again. The underlying run dispatches correctly (`MissionPlanService.dispatch_approved` → `handle_mission` → `system.execution.completed`), and the SSE stream from `events/bus.py` is publishing those completions in real time to the frontend — but no agent is subscribed, so no follow-up message ever appears in chat. This is the **single biggest UX gap for Tier 4 long-running autonomy** (core principle in AGENTS.md) — the system can run for hours but cannot tell you it's done without you asking. Structural root cause: **agent turns are request-response**. After `agent.run()` returns, there is no subscriber process on the mission session that can start a new turn when an interesting event arrives. The required primitive is a per-session "follow-up watcher" that: (a) stores a declared **follow-up intent** the Director writes when it promises to check back; (b) subscribes to the mission's event bus; (c) wakes on matching events; (d) spawns a fresh Director turn in the same session with the event as context; (e) the Director's reply streams into the existing chat SSE so the user sees a new assistant message appear unprompted. Requirements: (1) **schema** — new `session_followups` table: `id, session_id, mission_id, trigger_event_types: list[str], trigger_filter: jsonb (e.g. {"execution_id": "..."}), prompt_template: str ("The run you started earlier just completed — please summarize the result for the user and propose the next step"), created_by_agent: str, created_at, expires_at, consumed_at, cooldown_seconds: int, max_fires: int = 1`. Stored via a new `SessionFollowupService` + `SessionFollowupRepository`. (2) **Director tool** — `schedule_followup(trigger_events: list[str], filter: dict, prompt: str, expires_in_seconds: int = 86400)` that the Director calls whenever it says "I'll check back". The tool validates that the trigger events are in the known allowlist (see `EVENT_TYPE_REGISTRY` in `events/types.py:522+`) and persists a row. The Director's system prompt needs an explicit instruction: "When you dispatch a run or workflow on the user's behalf, ALWAYS call `schedule_followup` before your final message so you can continue the conversation without waiting for the user to prompt." (3) **Watcher process** — new `SessionFollowupWatcher` background service (follows the pattern of `mission_plan_daemon.py`) that boots with the event worker, subscribes to the mission event bus via `EventBus.subscribe_mission(mission_id)` (needs a new mission-scoped subscribe method — today `subscribe` is session-scoped at `events/bus.py:77`), and for each incoming event: query `session_followups` for rows where `trigger_event_types` contains the event type AND the filter matches AND `consumed_at IS NULL` AND `expires_at > now()`, then dispatch a new Director turn. The watcher does NOT itself reason — it only fires matches. (4) **Follow-up turn dispatch** — reuse `handle(session_id, message=<rendered prompt>)` from `agents/mission_control/mission_control.py` with the follow-up's `prompt_template` rendered against the event payload (e.g. `"Your dispatched run {execution_id} just completed with status={status}, cost=${total_cost_usd}, duration={duration_seconds}s. Summarize the result for the user and recommend the next step."`). The agent used is determined by the session's pinned agent (already stored on `session.agent_id`). The turn publishes `user.message` + `agent.response.*` events exactly as a human-initiated turn would, so the frontend SSE pipeline handles display with zero changes. Mark the follow-up row `consumed_at = utc_now()` after dispatch. (5) **Agent sprawl / cost guardrails** — follow-ups are a foot-gun for runaway cost; hard constraints: (a) `max_fires` defaults to 1 (a watcher fires once and is consumed); multi-fire follow-ups ("ping me every time a subtask completes") require explicit `max_fires > 1` and a `cooldown_seconds` between fires; (b) per-session cap: `sessions.max_active_followups = 5` in config so a confused Director cannot schedule 50 watchers on one session; (c) per-mission daily fire cap wired to the mission's `budget_usd_ceiling` — each follow-up turn costs LLM tokens and must be counted against the plan's `total_spent_usd` (reuse Plan 42 §10.7 budget logic); (d) `expires_at` default 24h; watcher cleans up expired rows on a cron. (6) **User control** — the user must be able to see + cancel pending follow-ups. Surface in the workspace center panel as a "Pending follow-ups" strip above the chat input: small chips like `"↻ checking back on run abc123 (expires 2h)"` with an × to cancel. Cancelling writes `consumed_at = utc_now()` with a reason. CLI: `mc mission followups list|cancel <id>`. (7) **Interaction with Plan 42 gate_mode** — in `autonomous` mode, the Director should proactively schedule a follow-up that also includes an implicit "start the next approved task" instruction, so the mission genuinely runs itself until it blocks or finishes. In `interactive`/`ai_assisted` mode, the Director schedules a follow-up that summarizes + asks for confirmation before the next step. The prompt template differs; the Director picks based on the mission's current gate_mode. (8) **Other agents, not just the Director** — the same `schedule_followup` tool should be wired into any vertical agent that dispatches long-running work (e.g. `mission.workflow.agent` when it kicks off a workflow run). The tool registration lives in `agents/mission_control/helpers/agent_setup.py` so any agent registered there picks it up via config. (9) **Event type allowlist** — the watcher should only care about completion-shaped events: `system.execution.completed`, `workflow.run.completed`, `workflow.execution.completed`, `mission_plan.dispatched` (as a "started" signal), `mission_plan.task_status_changed` with `to_status ∈ {completed,failed}`, `session.cost.threshold`, `system.budget.warning`. Not every event (flood). (10) **Failure path** — if the follow-up turn itself errors (LLM timeout, agent not in roster, etc.), write the error to `session_followups.failure_reason`, emit a `session.followup.failed` SystemEvent so the user sees *something* in chat, and do not retry automatically (avoid reentrant storms). (11) **Integration with the Autonomous Mission Roadmap** — this is a prerequisite for `docs/97-plans/46-plan-autonomous-mission-roadmap.md` Phase 2+; list it as a blocker in that doc. (12) docs — new `docs/99-reference-architecture/46-agentic-event-session-architecture.md` section on "Follow-up Intents" with the schema + watcher flow diagram. **Scope:** schema + service + tool + prompt update ≈ 1 day; the `subscribe_mission` method on the event bus + the watcher process ≈ 1 day; guardrails + UI strip + CLI ≈ 1 day. Total ≈ 3 focused days. **Why this unlocks more than it looks like:** once follow-ups exist, the Director stops being a chat assistant that happens to start runs and becomes a continuously-present mission conductor that reports in, flags problems, and drives to the next step — which is exactly the "mission outlives the session" primitive from AGENTS.md §1. Without it, Tier 4 autonomous is a theoretical goal the architecture cannot actually deliver.
